# RAG vs Long Context：检索、引用与遗漏控制

## 总览

这节课解决的问题是：业务知识到底应该“检索出来”，还是“直接塞进长上下文”？

RAG 和 long context 不是谁取代谁。它们解决的是不同约束下的上下文供给问题：

```text
RAG
  先从知识库里找相关材料，再把命中的片段交给模型。

Long Context
  把较长材料直接放进模型上下文，让模型在窗口内阅读和推理。

Hybrid
  先检索缩小范围，再把关键文档或结构化摘要放进长上下文。
```

在营销评估 Agent 里，这个选择很关键。指标口径、活动规则、数据字典、历史实验结论、合规边界都可能影响报告。如果上下文策略错了，Agent 可能引用过期口径、漏掉关键规则，或者把检索到的一段历史经验误当成当前事实。

## 任务开场

假设 Agent 要回答：

```text
为什么这次活动的 GTV uplift 比上次低？是否还值得继续投？
```

它可能需要这些知识：

```text
当前活动规则
GTV 指标口径
历史相似活动复盘
样本选择规则
投放渠道变化
补贴成本口径
因果诊断结果
业务方的预算约束
```

你不能简单地说“都放进 prompt”。也不能简单地说“做个向量库就行”。你要判断每类知识的更新频率、体量、精确性要求、引用要求和权限风险。

## 先做一遍

下面是一张简化决策表：

```text
知识类型             推荐策略             原因

指标口径             RAG + 版本引用        会更新，需要引用到具体版本
当前活动规则         直接上下文 + 人工确认  当前任务核心，不能靠相似文档猜
历史活动复盘         RAG                  文档多，只检索相似案例
数据字段字典         RAG + schema check    字段多，需要与真实数据检查结合
因果工具结果         直接上下文            当前运行产物，必须完整保留 warning
安全和因果规则       system/developer      规则优先级高，不应靠检索临时决定
```

这张表比“用不用 RAG”更重要。你是在给每类知识选择进入模型的路径。

## 拆开解释

RAG 的优势是可扩展和可更新。知识库可以保存大量文档，模型每次只拿到相关片段。对于指标口径、数据字典、历史实验、产品规则，这很适合。

RAG 的风险是遗漏。检索没召回关键文档时，模型可能仍然自信回答。它还可能只看到一个片段，看不到完整上下文。做 RAG eval 时，你不能只看最终答案，还要看召回文档是否正确、引用是否支持结论、有没有漏掉冲突材料。

Long context 的优势是减少检索丢失。当材料数量有限但内部关联复杂时，直接放进窗口可能更好。比如一次活动的完整规则、数据检查摘要、工具诊断和几段关键历史复盘，可以放进同一个上下文让模型综合。

Long context 的风险是噪音和位置。窗口越长，越需要结构化文档、清晰标签和引用要求。Anthropic 的 long context tips 强调长文档任务中材料位置、文档结构和引用的重要性。这对你意味着：长上下文不是“随便塞”，而是要设计阅读顺序和证据定位。

## 工程落地：四步法

第一步，给知识分类。

```text
稳定规则：system/developer 层固定，例如不能过度归因。
当前事实：直接上下文，例如当前活动配置和工具结果。
大量文档：RAG，例如历史复盘、指标文档、数据字典。
高风险缺口：人工确认，例如 treatment/control 定义不清。
```

第二步，给每类知识定义 freshness。

```text
daily：活动状态、预算、数据可用性。
weekly/monthly：指标口径、数据字典。
stable：因果结论边界、安全规则、报告结构。
```

第三步，设计引用和冲突处理。

```text
每个检索片段必须带 source_id、title、version、checked_at。
发现冲突口径时不能任选一个，要输出 conflict_detected。
没有召回关键口径时不能假设，输出 needs_more_context。
```

第四步，建立 RAG/long-context eval。

```text
retrieval_recall：该命中的文档是否命中。
groundedness：答案里的断言是否被引用支持。
conflict_handling：冲突材料是否被发现。
abstention：缺材料时是否拒绝或请求补充。
```

## 图解

```text
用户问题
  ↓
Knowledge Router
  ├─ 当前任务核心事实 → direct context
  ├─ 大量外部文档     → RAG
  ├─ 高优先级规则     → system/developer
  └─ 不可确定缺口     → ask human
  ↓
Context Packet with citations
  ↓
Model answer with boundaries
```

这个 `Knowledge Router` 是产品能力，不是模型凭感觉决定。

## 工业视角

OpenAI file search 文档把 file search 描述为让模型在回答前搜索已上传文件知识库的工具，并提到语义和关键词搜索、vector stores 等机制。这里的可迁移点是：知识库连接正在变成工具化能力，模型不需要把所有知识都记在参数里。

Anthropic long context tips 强调长文档输入的结构、位置和引用。这里的工程推论是：长窗口适合承载复杂材料，但仍然需要清晰的文档边界和证据提取。

MCP 的 resources/tools 思路也可以迁移到 RAG：知识不是散落在 prompt 里的文字，而是可以通过资源、工具和协议暴露给模型应用。

## 常见误区

第一个误区是认为“用了 RAG 就准确”。RAG 只增加了可访问知识，不保证检索命中、引用正确或推理正确。

第二个误区是认为“上下文窗口够长就不需要 RAG”。如果知识库持续更新、文档很多、权限复杂，全部塞进长上下文既贵又难控。

第三个误区是没有引用要求。没有 source/version/checked_at，业务用户很难判断结论是否基于当前口径。

第四个误区是忽略冲突材料。营销口径经常有版本差异，Agent 必须能说“存在冲突，不能直接下结论”。

## 迁移练习

把知识策略表迁移到客服 Agent：

```text
政策文档：RAG + 版本引用。
用户订单：实时工具查询。
安全规则：system/developer。
用户历史偏好：memory，需要隐私控制。
不确定投诉场景：人工转接。
```

你会看到同一个框架可以迁移，但每类知识的风险不同。客服 Agent 更怕越权和隐私，营销评估 Agent 更怕过度归因和口径错误。

## 总结回扣

RAG 和 long context 都是在解决“模型应该看见什么”的问题。

RAG 适合大量、可更新、需要按需召回的知识。Long context 适合有限但关联复杂、需要整体阅读的材料。Direct context 适合当前任务的核心事实和工具结果。System/developer 适合高优先级规则。Human confirmation 适合缺口高风险、不能猜的场景。

真正的能力不是说出 RAG 的定义，而是给每类业务知识选择正确路径，并为遗漏、冲突和过期设计 fallback。
