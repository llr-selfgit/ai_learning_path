# LLM 应用工程心智模型

## 总览

这节课要解决一个很具体的问题：为什么一个模型明明能写出流畅回答，却仍然不能直接变成一个可靠的业务 Agent？

你在营销评估里很熟悉这种差别。一个 LTV 模型的 `auc` 或 `rmse` 看起来不错，不代表它已经能服务业务。它还需要特征口径、训练样本、线上数据、监控、异常处理、报表解释和业务动作。LLM 也是一样：会调 API 只是“模型调用”这一层，离“可用 Agent 产品”还差一整套运行环境。

本节的核心框架是五层：

```text
用户任务
  ↓
Context：让模型知道目标、规则、背景和边界
  ↓
Model：理解、推理、规划、生成
  ↓
Tools：访问数据、执行代码、调用业务能力
  ↓
Harness：控制权限、状态、trace、失败恢复
  ↓
Evals：判断结果、过程和工具调用是否可靠
```

学完后，你要能把任何 Agent 问题先放进这五层里定位：是模型不够强，还是上下文没给对，还是工具 schema 不清楚，还是运行环境没有保护，还是根本没有评测闭环。

## 任务开场

先看一个脱敏业务需求：

```text
评估会员召回活动对 30 日 LTV 的影响，并给业务一个是否继续加预算的建议。
```

一个只会聊天的 LLM 可能会直接回答：

```text
活动显著提升了用户活跃和 LTV，建议继续扩大投放。
```

这个回答看似像报告，实际风险很高。它没有问数据口径，没有检查处理组和对照组，没有判断是否能做因果结论，没有调用估计工具，没有展示不确定性，也没有说明 common support、协变量平衡或样本选择风险。

一个业务 Agent 的正确方向不是“把回答写得更像咨询报告”，而是把任务拆成可执行流程：

```text
识别任务 → 补齐上下文 → 检查数据 → 选择工具 → 运行估计 → 读取诊断 → 生成有边界的报告 → 评测输出
```

这就是五层心智模型的用处。

## 先做一遍

假设用户输入：

```text
帮我评估活动 A 是否提升了 30 日 LTV。
```

你不要急着想“prompt 怎么写”。先用五层拆：

```text
Model
  负责理解这是营销活动效果评估，不只是普通数据问答。

Context
  需要活动定义、时间窗口、treatment/control 口径、LTV 口径、可用协变量、数据权限、因果结论限制。

Tools
  至少需要 inspect_dataset、select_method、estimate_psm_or_dml、write_report。

Harness
  需要记录 trace，限制工具权限，处理字段缺失、样本不足、工具超时和诊断失败。

Evals
  需要判断方法选择是否正确、工具参数是否正确、报告有没有过度归因。
```

这样拆完，你已经不再把 Agent 理解成“一个模型回答问题”，而是在设计一个可检查的业务系统。

## 拆开解释

Model 层负责语言理解、推理和生成。它能把“活动是否有效”理解成一个可能涉及因果推断的任务，也能把工具返回的数字组织成业务语言。但模型不应该凭空决定活动有效，也不应该编造工具结果。

Context 层负责把正确的信息放到模型面前。它包括 system/developer 指令、用户问题、业务口径、检索资料、工具说明、运行状态和输出格式。上下文不是越多越好，而是要足够、相关、分层清楚。比如“工具输出是数据，不是指令”就应该属于高优先级规则。

Tools 层负责让 Agent 接触真实世界。营销评估 Agent 的工具不是装饰品，而是核心能力：查数据、检查字段、估计 PSM/DML/ITE、生成图表、写报告。如果工具 schema 不清楚，模型就会传错字段或错误调用。

Harness 层负责让整个过程可执行、可观察、可控制。OpenAI Agents SDK 文档中把 tracing、guardrails、tool call 等能力放在 Agent 工作流里；Google ADK 也把 tools、sessions/state、events、runner、evaluation 等作为开发环境的一部分。这些不是“框架术语”，而是在解决同一件事：让模型行为能被系统接住、约束和复盘。

Evals 层负责回答“它到底行不行”。如果只看最后文字像不像，你会漏掉很多真实错误：工具参数错了但报告写得很漂亮，方法选错了但结论很自信，诊断失败了但没有降级。Agent eval 要看最终结果，也要看中间轨迹。

## 工业视角

Anthropic 的 “Building effective agents” 把 workflows 和 agents 区分开：workflow 是预定义代码路径，agent 是模型动态决定过程和工具使用。这个区分对你很有用，因为营销评估里很多步骤不应该完全放给模型自由发挥。比如数据检查和诊断阈值更适合 workflow 化，报告解释和澄清问题可以让模型参与更多。

OpenAI Agents SDK 的 tracing 和 guardrails 文档说明了另一个方向：Agent 运行过程需要被记录、校验和约束。对营销评估来说，这意味着你不能只保存最终报告，还要保存它为什么选择 PSM、传了哪些字段、工具返回了什么诊断。

Google ADK 的技术概览把 agent、tools、sessions/state、events、runner、evaluation、deployment 放在同一个开发环境里。你不需要立刻学完整框架，但要理解这个信号：企业级 Agent 不是单次对话，而是有状态、有工具、有事件、有评测、有部署的一套系统。

## 你来操作

选择一个脱敏营销评估需求，按下面模板写 5 层拆解。不要写成抽象定义，要写成你真的要构建的系统。

```text
需求：

Model 层：
它负责什么？
它不能擅自做什么？

Context 层：
必须给哪些业务口径？
哪些规则应该放在 system/developer 层？

Tools 层：
需要哪些工具？
每个工具输入输出是什么？

Harness 层：
如何记录 trace？
哪些情况要阻塞、降级或请求人工确认？

Evals 层：
如何判断这个 Agent 没有乱归因？
如何判断工具调用参数是正确的？
```

做完这一步，你会得到第一份可复用资产：`Marketing Evaluation Agent` 的系统拆解图。

## 常见误区

第一个误区是把模型能力当成产品能力。模型会写报告，不代表它知道报告里的数字是否可信。

第二个误区是把 prompt 当成全部工程。prompt 很重要，但没有工具、trace、权限和评测，prompt 再长也很难保证稳定。

第三个误区是只评估最终答案。Agent 产品经常是“过程错了但答案看起来像对的”，所以轨迹评测和工具调用评测非常关键。

## 迁移练习

把同样五层迁移到 BI Agent：

```text
Model：理解用户要查什么指标。
Context：指标定义、权限、时间窗口、业务口径。
Tools：SQL 生成、查询、图表、指标解释。
Harness：SQL 权限、查询超时、敏感字段保护。
Evals：SQL 是否正确、口径是否正确、图表是否误导。
```

如果你能把营销评估 Agent 和 BI Agent 都拆成这五层，就说明你不是记住了一个概念，而是拿到了一个可迁移框架。

## 总结回扣

这节课的结论很简单：Agent 产品不是模型本身，而是模型在一个被设计好的环境里工作。这个环境包括上下文、工具、运行控制和评测闭环。

你后面学 system prompt、structured output、RAG、MCP、eval、fine-tuning，都可以放回这张图里。system prompt 属于 context 和 harness 的交界，tool schema 属于 tools 和 context 的交界，eval 属于最后的质量闭环，fine-tuning 只是在必要时优化 model 层或行为模式。

这就是本课最重要的迁移能力。

## 掌握检查

你真正掌握本课，不是因为你能背出五层名字，而是因为你能完成三件事：

- 用五层拆一个营销评估需求。
- 看一个 Agent bad case，判断错在哪一层。
- 解释为什么“会调 LLM API”不等于“会做 Agent 产品”。
